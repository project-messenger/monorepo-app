# Модель пространств, проектов, каналов и прав доступа

[← к бэклогу](./README.md) · Jira: —

## Зачем

ТЗ просит определиться с моделью до основной разработки: от неё зависят схема БД, проверки прав в HTTP и WebSocket,
поиск и ИИ. Если каждый решит «кто что может» в своей задаче, правила разъедутся. Что требует ТЗ —
[docs/product.md](../product.md#модель-предметной-области).

## Решения до начала

- [x] Роли определены на двух уровнях: Workspace (`Owner`, `Admin`, `Member`) и Project
      (`Project Admin`, `Developer`). Решение зафиксировано в [ADR-0014](../adr/0014-access-model.md).
- [x] Матрицы прав Workspace и Project согласованы: полномочия по управлению участниками, ролями,
      проектами, каналами, GitHub-интеграцией и стендапами зафиксированы в
      [docs/permissions.md](../permissions.md).
- [x] Участие в Workspace не предоставляет автоматического доступа к проектам и их открытым каналам.
      Открытые каналы доступны участникам соответствующего проекта. Правила доступа описаны в
      [docs/permissions.md](../permissions.md).
- [x] Личные и групповые переписки существуют на уровне Workspace, вне проектов.
      Доступ к переписке имеют только её участники. Правила описаны в
      [docs/permissions.md](../permissions.md).
- [ ] Доступ к данным приватного GitHub-репозитория: согласован принцип отдельной проверки прав
      без автоматического раскрытия содержимого участникам Workspace.
      Требуется уточнить доступ к отдельным видам данных GitHub.
      См. [docs/permissions.md](../permissions.md).

Вопросы ниже всплыли в KAN-33 (realtime, [ADR-0011](../adr/0011-realtime-messaging.md)). Предложения подготовил
ИИ-агент, foxprogs с ними согласен; решает команда.

- [ ] **Каналы и переписки: одна таблица или две.** Предложение: одна таблица переписок с полем `kind` (`channel`,
      `group`, `dm`, `self`) и `project_id`, который есть только у канала. У сообщений, тредов, реакций и счётчика
      канала (ADR-0011) тогда одна ссылка. Различия — кому принадлежит (проекту или пространству), кто создаёт, задачи
      и решения только из канала, открытый или закрытый — задаются правами и ограничениями. Так устроены Mattermost
      (тип канала) и Slack API (`conversations.*`). При двух таблицах у `messages` два nullable-FK или дублирование
      сообщений, тредов и реакций, а id из разных таблиц могут совпасть.
- [ ] **«Избранное»** — место, куда скинуть заметку или отложить сообщение себе, как в Telegram. Предложение:
      переписка `kind = 'self'` с одним участником, создаётся автоматически. Тогда не нужно заводить чат, добавлять
      кого-то и удалять. Решить: одна на пространство или одна на пользователя; сохранить сообщение из канала — это
      копия или ссылка. Копия останется у человека после исключения из закрытого канала.
- [ ] **Ограничения в БД.** Права проверяются в бэкенде, а то, что дёшево, дублируется в схеме:
  - `CHECK`: у канала есть `project_id`, у переписок его нет;
  - «задача и решение — только из канала»: составной FK. У переписок `UNIQUE (id, kind)`, у задачи —
    `conversation_kind text NOT NULL DEFAULT 'channel' CHECK (conversation_kind = 'channel')` и
    `FOREIGN KEY (conversation_id, conversation_kind)`. `NOT NULL` обязателен: если хоть одно поле составного FK
    равно `NULL`, Postgres связь не проверяет (MATCH SIMPLE по умолчанию). `conversation_id` остаётся nullable:
    задачу можно создать и не из сообщения ([product.md](../product.md#задачи-и-канбан)).
- [ ] **RLS** (Row Level Security в Postgres). Предложение: не сейчас. Бэкенд ходит в БД одним пользователем через
      пул соединений. Для RLS пришлось бы в каждой транзакции передавать id пользователя (`SET LOCAL`), а в Drizzle
      ([ADR-0012](../adr/0012-orm-drizzle.md)) это ручная обвязка вокруг каждой транзакции. Права проверяются в
      одном месте на бэкенде (см. «Что сделать»). Вернуться, если понадобится вторая
      линия защиты.
