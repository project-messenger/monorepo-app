# 0012. ORM для бэкенда: Drizzle v1

- **Статус:** принято
- **Дата:** 2026-11-21
- **Область:** api
- **Подготовил:** ИИ-агент по запросу foxprogs: сравнение ORM и прототип. Решение принял foxprogs (2026-11-21) по
  итогам прототипа.
- **Задача:** [KAN-42](https://project-group-11.atlassian.net/browse/KAN-42)

## Контекст

В [docs/product.md](../product.md#что-ещё-не-решено) стоит «ORM: Prisma или TypeORM, ADR при подключении БД». К
подключению БД появились требования, от которых зависит выбор:

- **Realtime ([ADR-0011](./0011-realtime-messaging.md)).** Дубли отсекает `UNIQUE (user_id, client_id)`. Номер
  сообщения в канале выдаётся запросом `UPDATE … SET last_seq = last_seq + 1 … RETURNING last_seq` в той же
  транзакции, что и вставка. Этот `UPDATE` сам блокирует строку канала до коммита. Повтор отправки ловится по ошибке
  уникальности (код Postgres `23505`): транзакция откатывается вместе со счётчиком, сервер читает уже сохранённое
  сообщение и отвечает успехом. Нужна ORM, в которой этот SQL пишется прямо и видно, какие запросы уходят в БД.
- **Ограничения в схеме ([backlog/domain-model.md](../backlog/domain-model.md)).** Предлагаются `CHECK` и составной
  FK (`conversation_id`, `conversation_kind`) → `UNIQUE (id, kind)`. Хорошо, если миграции генерируются из схемы, а не
  дописываются руками.
- **Поиск и ИИ** (отдельный ADR, когда дойдём). Скорее всего, полнотекстовый поиск и векторы (pgvector) в той же
  базе. ORM не должна закрывать эту дорогу.
- **Контракт ([ADR-0009](./0009-api-contract-openapi-orval.md)).** DTO — Zod-схемы, не модели ORM. От ORM нужны только
  схема БД, запросы и миграции.
- **Стек.** NestJS 12, ESM (`"type": "module"`), Node 24 в CI, Postgres 18
  ([ADR-0010](./0010-local-infrastructure.md)).
- **Команда.** Два бэкендера на неполный день, оба пишут код с ИИ-агентами.

Состояние на 2026-11-21 (по npm, GitHub и официальной документации):

| Пакет                     | Стабильная             | Следующая                              |
| ------------------------- | ---------------------- | -------------------------------------- |
| Prisma                    | 7.10.1                 | 8.0.0-rc (`npm i prisma` уже ставит 8) |
| Drizzle ORM / Drizzle Kit | 0.45.4 / 0.31.11       | 1.0.0-rc.6 / 1.0.0-rc.6                |
| TypeORM                   | 1.1.3 (1.0 — май 2026) | —                                      |
| `@nestjs/drizzle`         | 0.0.2 (пакет новый)    | —                                      |

## Варианты

1. **Prisma 7.** Схема в `.prisma`, сгенерированный клиент.
   - Плюсы: стабильная; ИИ-агенты знают её лучше всех; счётчик из ADR-0011 пишется штатно
     (`data: { lastSeq: { increment: 1 } }`); дубль — понятный код `P2002`; есть официальные skills для агентов.
   - Минусы: `CHECK` в схеме не поддерживается (дописывать в миграцию руками и не потерять при следующей генерации);
     полнотекстовый поиск — preview-флаг, pgvector — только сырой SQL; нужен шаг `prisma generate`; модуля Nest нет
     (известный шаблон `PrismaService`). Это последняя версия поколения: в Prisma 8 другой API, и переход — переписать
     все запросы. Седьмую поддерживают 18 месяцев после выхода восьмой. Ловушка: `npx prisma` и `npm i prisma` уже
     ставят 8, версию 7 нужно закреплять явно.
2. **Prisma 8 (RC).** Новый продукт: `contract.prisma`, запросы `db.orm.public.X.where().first()`.
   - Плюсы: `CHECK`, pgvector, полнотекстовые индексы в схеме; skill для агентов идёт внутри пакета.
   - Минусы: релиз обещали на октябрь 2026, сорвали, новой даты нет; от RC1 до RC22 около 400 ломающих изменений,
     документация предупреждает, что API ещё изменится. Нет `increment` (счётчик — через блокировку и JS или сырой
     SQL), вложенных записей, привычных кодов ошибок. Строить проект на RC с такой скоростью изменений — не сейчас.
3. **Drizzle 0.45.** Схема на TypeScript (`pgTable`), запросы — построитель SQL (`select().from().where()`).
   - Плюсы: стабильная, патчи выходят; запросы читаются как SQL: счётчик —
     ``set({ lastSeq: sql`${t.lastSeq} + 1` })`` + `.returning()`, блокировки — `.for('update')`, конфликт —
     `onConflictDoNothing({ target: [...] })`; `CHECK`, составные FK и unique в схеме; тип `vector` и индексы HNSW
     штатно; без генерации клиента; ближе всего к SQLAlchemy Core.
   - Минусы: сайт документации уже описывает v1, для 0.45 агент может взять чужой синтаксис; старый механизм `casing`
     авторы называют источником ошибок; переход на v1 затронет связи, casing и миграции; дубль приходит как ошибка
     драйвера `pg`, код `23505` разбирать самим.
4. **Drizzle v1 (RC, версия закреплена).** То же, что 0.45, плюс новый API связей и casing.
   - Плюсы: документация совпадает с кодом; основной синтаксис запросов не менялся с бет; у Drizzle Kit есть skills
     для агентов (`drizzle-kit skills`).
   - Минусы: RC без объявленной даты релиза; в rc.5 и rc.6 около 40 ломающих изменений (в основном связи,
     кодеки, ошибки и драйверы, а не `select`/`insert`/`update`); обновление между RC — с чтением changelog.
5. **TypeORM 1.x.** Сущности на декораторах, Active Record / Data Mapper.
   - Плюсы: живая, есть `@nestjs/typeorm`, блокировки, `@Check`, `vector`/`tsvector`.
   - Минусы: слабая типизация результатов запросов; `bigint` по умолчанию строка; неявное поведение (lazy-связи,
     `save` с каскадами) прячет SQL — плохо для ADR-0011; ИИ часто пишет код под 0.3, а не под 1.x.
6. **MikroORM** (рассматривали кратко). Unit of Work, ближе к SQLAlchemy ORM. Отпал: неявный flush прячет SQL,
   ИИ-агенты знают его хуже остальных.

Код realtime у Drizzle 0.45 и v1 одинаковый (прототип запускал один и тот же файл на обеих). Разница между ними —
связи (relational queries), casing, документация и формат миграций (см. «Проверка на прототипе»).

## Решение

**Drizzle v1: `drizzle-orm@1.0.0-rc.6` + `drizzle-kit@1.0.0-rc.6`**, версии закреплены точно (без `^` и `~`), драйвер
`pg` (node-postgres), подключение к Nest — `@nestjs/drizzle`.

Почему Drizzle, а не Prisma 7. Основная сложность бэкенда — realtime по ADR-0011, проверки прав в БД на каждом событии,
а потом поиск и контекст для ИИ. Везде нужен SQL, который видно и контролируешь, и ограничения в самой БД. Drizzle даёт
это штатно, а Prisma 7 — через ручные правки миграций и сырой SQL. Плюс то, что учим на Drizzle, переносится в его
1.0, а API Prisma 7 в восьмой версии уже заменён.

Почему v1 RC, а не стабильная 0.45. На прототипе обе прошли все проверки одним и тем же кодом. Решили две вещи:

- **миграции двух бэкендеров не конфликтуют.** В v1 каждая миграция — своя папка с отметкой времени, общего журнала
  нет. В 0.45 у двух веток получается одинаковый номер миграции и конфликт в `meta/_journal.json`, а если при merge
  оставить журнал одной ветки, миграция второй молча не применяется;
- **документация на сайте Drizzle описывает v1**, и ИИ-агент возьмёт синтаксис оттуда.

Цена — RC без даты релиза: перед обновлением версии читаем changelog (в rc.5 и rc.6 было около 40 ломающих изменений,
в основном связи, кодеки и драйверы). Если RC начнёт мешать, откат на 0.45 на старте дешёвый: запросы те же, меняется
формат миграций.

Чем Prisma 7 сильнее и что мы теряем: стабильность прямо сейчас, лучшее знание ИИ, `P2002` вместо разбора ошибок
драйвера.

Соглашения:

- **Имена таблиц, колонок и ограничений пишем явно** в snake_case: `uuid('user_id')`, `pgTable('messages', …)`,
  `unique('messages_user_client_unique')`. Опцию `casing` не используем. Имя ограничения нужно, чтобы по нему понять,
  какая уникальность нарушена.
- **Миграции создаём `drizzle-kit generate`, применяем `drizzle-kit migrate`.** Папку каждой миграции коммитим
  целиком: `migration.sql` и `snapshot.json`. По снимкам `drizzle-kit` считает следующую миграцию и проверяет
  конфликты (`check`); без них `generate` построит неверный дифф. `drizzle-kit push` — только для одноразовых
  экспериментов.
- **Запросы — построитель SQL** (`select`/`insert`/`update`/`delete`, `db.transaction`). Relational queries
  (`db.query.*`) — только для чтения со связями.
- **Ошибка уникальности** разбирается одной функцией-помощником (например, `isUniqueViolation(err, constraintName)`),
  а не в каждом сервисе. Drizzle бросает `DrizzleQueryError` (экспорт из `drizzle-orm`), в его `cause` — ошибка `pg`
  с полями `code` (`'23505'`) и `constraint`.
- **Конфликт миграций после merge main** проверяем `drizzle-kit check`.
- **Модели Drizzle не уходят в контракт:** DTO по-прежнему Zod-схемы (ADR-0009).

## Проверка на прототипе

Прототип одноразовый, **вне монорепы**, как в ADR-0011: в `apps/api` пакеты не добавлялись. Две папки с одинаковым
кодом: drizzle-orm 1.0.0-rc.6 + drizzle-kit 1.0.0-rc.6 и drizzle-orm 0.45.4 + drizzle-kit 0.31.11. Общее: `pg` 8.23.1,
NestJS 12.6.0, `@nestjs/drizzle` 0.0.2, TypeScript 6 (strict, `nodenext`), Postgres 18.7 из `pnpm infra:up`. Проверки —
скриптами; v1 — на Node 26 и Node 24.

Схема: `conversations` (`kind`, `project_id`, `last_seq`, `UNIQUE (id, kind)`, два `CHECK`), `conversation_members`
(составной PK), `messages` (`UNIQUE (user_id, client_id)`, `UNIQUE (conversation_id, seq)`, `CHECK (length(text) > 0)`),
`tasks` (`conversation_kind` с `CHECK` и составной FK → `conversations (id, kind)`) — по
[backlog/domain-model.md](../backlog/domain-model.md).

| Проверка                                                                                                         | v1 RC | 0.45 |
| ---------------------------------------------------------------------------------------------------------------- | ----- | ---- |
| `drizzle-kit generate` выдаёт `CHECK`, составной PK, составной FK и unique без правок руками                     | да    | да   |
| Повторный `generate` без изменений схемы: «No schema changes»                                                    | да    | да   |
| В БД работают: канал без проекта и пустой текст — `23514`, задача из группы — `23503`, из канала — принята       | да    | да   |
| Счётчик уходит одним запросом `update … set "last_seq" = "conversations"."last_seq" + 1 … returning`             | да    | да   |
| 50 параллельных отправок в канал: `seq` подряд, без дыр и повторов                                               | да    | да   |
| Тот же `clientId` 10 раз параллельно и ещё раз: одно сообщение, все ответы с одним id, счётчик откатился         | да    | да   |
| Ошибка дубля: `DrizzleQueryError`, в `cause` — `code = '23505'`, `constraint = 'messages_user_client_unique'`    | да    | да   |
| `.for('update')` → `… for update`                                                                                | да    | да   |
| `DrizzleModule.forRootAsync` + `ConfigService` + `@InjectDrizzle()`: запрос из сервиса, пул закрыт при `close()` | да    | да   |
| `tsc --strict` с `skipLibCheck: true` (как в `apps/api`)                                                         | да    | да   |
| Две ветки параллельно добавили миграции, merge: без конфликтов, `check` ок, `migrate` применил обе               | да    | нет  |

Что ещё заметили:

- В 0.45 миграции называются `0001_x.sql` и записываются в общий `meta/_journal.json`. После параллельных веток —
  конфликт в журнале и в `meta/0001_snapshot.json`. Если оставить журнал одной ветки, файл второй остаётся в папке, но
  не применяется и ошибки нет.
- В v1 rc.6 с `skipLibCheck: false` — 4 ошибки в `.d.ts` самого Drizzle. В `apps/api` стоит `skipLibCheck: true`, так
  что это не мешает.
- Имена по умолчанию: v1 — как в Postgres (`…_pkey`, `…_fkey`), 0.45 — свои (`…_pk`, `…_fk`).
- `@nestjs/drizzle` 0.0.2 сам закрывает пул при остановке и логирует ошибки соединения. Свой провайдер не понадобился.

Что не проверяли:

- в `apps/api` ничего не подключали, поэтому `pnpm --filter api lint`, `test` и `build` с Drizzle ещё не запускались —
  это задача на подключение БД;
- relational queries (`db.query.*`) и связи;
- pgvector (в образе `postgres:18.7-bookworm` расширения нет, это вопрос ADR про поиск) и полнотекстовый поиск.

## Последствия

- Запросы и миграции — обычный SQL, его видно в коде и в логах. Ограничения живут в схеме и проверяются генерацией.
- Учим построитель запросов, а не «магию» ORM. Для разработчика из SQLAlchemy: `pgTable` ≈ `Table`,
  `select().from().where()` ≈ `select().where()`, `.for('update')` ≈ `with_for_update()`, `onConflictDoNothing` ≈
  `on_conflict_do_nothing()`, `db.transaction` ≈ `with session.begin()`.
- Больше ручной работы, чем в Prisma: разбор ошибок драйвера, связи пишем явнее, хорошие практики — свои.
- На v1 RC: обновление версии — отдельный PR с чтением changelog. Выйдет 1.0 — переходим на неё.
- Следующая задача — подключение БД в `apps/api`: пакеты с версиями выше, модуль с `DrizzleModule.forRootAsync`,
  папка миграций, скрипты `db:generate` / `db:migrate` / `db:check`, помощник для ошибки уникальности с тестом.

  [`apps/api/README.md`](../../apps/api/README.md), [docs/architecture.md](../architecture.md),
