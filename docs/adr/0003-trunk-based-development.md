# 0003. Trunk-based development и squash merge

- **Статус:** принято
- **Дата:** 2026-11-14 (решение действует с создания репозитория, записано задним числом)
- **Область:** весь проект
- **Подготовил:** ИИ-агент (Claude Code) по запросу foxprogs
- **Задача:** [KAN-15](https://project-group-11.atlassian.net/browse/KAN-15)

## Контекст

ТЗ требует:

- работу с Git по trunk-based подходу;
- запрет прямого пуша в основную ветку — только через PR с код-ревью, причём перекрёстное: смотрит не только тимлид;
- на каждый PR — линтеры, тесты, сборку и typecheck в CI;
- релиз — отведением ветки и кнопкой release в GitHub.

Кроме того, у нас 7 человек с частичной занятостью, много кода от агентов. Долгоживущие ветки дают большие
конфликты, а большие PR никто не успевает отревьюить.

## Варианты

Сам подход задан ТЗ. Выбирали, как вливать PR:

1. **Merge-коммит.** В `main` попадают все промежуточные коммиты («fix», «wip»), история читается тяжело.
2. **Rebase.** Линейная история, но промежуточные коммиты тоже попадают в `main`.
3. **Squash.** Один PR — один коммит в `main` с понятным заголовком.

## Решение

Короткие ветки от `main` (ориентир — до 3 дней), squash merge. На `main` действует ruleset: только PR, 1 approve,
закрытые обсуждения, зелёный CI, только squash. Подробные правила — [`docs/workflow.md`](../workflow.md).

## Последствия

- Заголовок PR становится коммитом в `main`, поэтому он в формате коммита.
- Незаконченную фичу вливаем скрытой (не подключена к роуту или выключена флагом).
- Релизный процесс (ветка + кнопка release) ещё не настроен — отдельная задача.
