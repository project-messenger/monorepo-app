# 0013. Вход: серверная сессия в cookie через `@nestjs/authentication`

- **Статус:** принято
- **Дата:** 2026-11-25
- **Область:** api, web
- **Подготовил:** ИИ-агент по запросу foxprogs: варианты, черновик ADR и контракт. Решения принял foxprogs: сессия
  вместо JWT (2026-11-24), пакет `@nestjs/authentication` и вход без «Запомнить меня» (2026-11-25), по замечаниям
  ревью — защита от CSRF на всё API уже в PR 1 и отключение сокетов при выходе (2026-11-25).
- **Задача:** [KAN-51](https://project-group-11.atlassian.net/browse/KAN-51)

## Контекст

Нужны регистрация и вход по email и паролю. Вход через GitHub — отдельная задача
([KAN-56](https://project-group-11.atlassian.net/browse/KAN-56)), но решение не должно ему мешать.

Что важно для выбора:

- **ТЗ не требует JWT** и вообще не задаёт способ входа. Оно требует проверять права не только в HTTP, но и в событиях
  WebSocket, поиске, файлах и запросах к ИИ, а удалённый участник не должен получать новые сообщения.
- **Права всё равно проверяются по БД** на каждый запрос и событие ([ADR-0011](./0011-realtime-messaging.md)). Значит,
  «не ходить в БД», ради чего обычно берут JWT, мы не выигрываем.
- **Фронтенд и бэкенд на разных origin:** `localhost:3000` и `localhost:3001`. Клиент Orval ходит на
  `NEXT_PUBLIC_API_URL`.
- **Команда:** два бэкендера на неполный день. Чем меньше своего кода безопасности, тем лучше.

## Варианты

1. **JWT (access) + refresh-токен в `httpOnly`-cookie.** Плюсы: популярно, бэкенд может не хранить сессии. Минусы:
   access-токен нельзя отозвать до истечения срока; нужны ротация refresh, обнаружение повторного использования,
   хранение refresh в БД — то есть и токены, и таблица. Нам это ничего не даёт: права всё равно в БД.
2. **Серверная сессия, своя реализация.** Случайный токен в `httpOnly`-cookie, в таблице `sessions` — его хеш. Плюсы:
   просто понять, сессию можно удалить в любой момент. Минусы: хеширование паролей, guard, cookie, защита от фиксации
   сессии и от подбора по времени ответа — всё пишем и тестируем сами.
3. **Серверная сессия через [`@nestjs/authentication`](https://docs.nestjs.com/security/authentication.md).**
   Официальный пакет Nest (MIT, без сторонних зависимостей). Даёт то же, что вариант 2, готовым: `PasswordHasher`
   (scrypt, одинаковое время ответа для неизвестного email), `SignInService` (ставит cookie, удаляет старую сессию при
   входе, отказывает чужим origin), глобальный guard с `@Public()` и `@CurrentUser()`, проверку сессии для WebSocket.
   Хранилища (`SessionStore`) пишем сами на Drizzle. Минусы: пакет молодой (0.1.x, с сентября 2026), его API новее
   знаний большинства ИИ-моделей — сверяемся с README и типами пакета.

## Решение

**Вариант 3.** Сессия на сервере — её можно удалить в любой момент (выход, выход со всех устройств), а права и так
проверяются по БД. Готовый пакет вместо своего кода — меньше мест, где можно ошибиться в безопасности.

Как это устроено:

- **Cookie.** Пакет ставит `httpOnly`-cookie `__Host-sid` со случайным 256-битным токеном. В БД хранится только
  SHA-256 токена, поэтому утечка таблицы не даёт войти. Фронтенд cookie не читает и не хранит токен сам.
- **Срок сессии один для всех:** не больше 30 дней с входа и истекает после 7 дней без активности. Галочки «Запомнить
  меня» нет: пакет задаёт срок на всё приложение, а не на каждый вход. Дизайна страниц входа и регистрации ещё нет;
  форма в `apps/web/src/features/auth` — заготовка из шаблона, а не принятый дизайн.
- **Хранилище.** Таблицы `users` (email уникальный, в нижнем регистре; `password_hash` может быть пустым — для входа
  только через GitHub) и `sessions` (поля по `SessionRecord` пакета). Store на Drizzle регистрируется в пакете; хранение
  в памяти — только в тестах.
- **Разные origin.** CORS с `credentials: true` для `CORS_ORIGIN`, фронтенд шлёт запросы с `credentials: 'include'`.
- **CSRF.** CORS от него не защищает: браузер всё равно отправит `POST` с чужого сайта вместе с cookie, CORS только не
  даст тому сайту прочитать ответ. Поэтому две проверки с одним списком `trustedOrigins` = `[CORS_ORIGIN]`:
  - [`app.enableCsrfProtection()`](https://docs.nestjs.com/security/csrf.md) — встроена в Nest с 12.1, включена в
    `apps/api/src/app.setup.ts` уже в PR 1. Отвечает 403 на `POST`, `PUT`, `PATCH`, `DELETE` с чужого origin **до**
    разбора тела, guard и обработчика, на любом пути. Без неё регистрация с чужого сайта создала бы пользователя
    раньше, чем пакет откажет в сессии;
  - `session.trustedOrigins` пакета — он не принимает cookie сессии на изменяющих запросах и при подключении
    WebSocket с чужого origin. Документация пакета просит передавать обеим проверкам одинаковый список;
  - `localhost:3000` → `localhost:3001` — разные origin, но один сайт: браузер шлёт `Sec-Fetch-Site: same-site`, и
    без адреса фронтенда в `trustedOrigins` его запросы получали бы 403. Адреса из CORS сюда сами не попадают;
  - `GET`, `HEAD`, `OPTIONS` не проверяются, поэтому `GET` ничего не должен менять. Запросы без заголовков браузера
    (`curl`, тесты, сервер → сервер) проходят;
  - вебхуки GitHub приходят без `Origin` и тоже проходят. Если какой-то отправитель пришлёт чужой `Origin`, его путь
    добавим в `exclude`, а не отключим проверку.
- **В проде** фронтенд и API должны быть на одном сайте (например, `app.example.com` и `api.example.com`) или за одним
  доменом через прокси: иначе браузер не отправит cookie.
- **WebSocket** узнаёт пользователя по той же cookie при подключении: `WsAuthenticator.authenticateConnection()` в
  `handleConnection()` (guard там не работает). Подключение с чужого сайта анонимно и закрывается. Дальше guard
  проверяет сессию на каждом входящем сообщении, поэтому после выхода сокет не может ничего отправить. Но рассылки
  сервера в комнаты сессию не проверяют — об этом следующий раздел.

### WebSocket после выхода

Сессия удалена, а открытый сокет остаётся в комнатах каналов и получает новые сообщения до переподключения. Проверка
членства ([ADR-0011](./0011-realtime-messaging.md)) не помогает: человек по-прежнему участник каналов. Поэтому:

- При подключении сокет входит не только в `user:<userId>` (ADR-0011), но и в `session:<sessionId>`.
- **Выход** (`logout`): удалить сессию, затем `io.in('session:<sessionId>').disconnectSockets()`. Закрываются
  только соединения этого браузера, другие устройства работают. Порядок важен: если отключить раньше, клиент может
  успеть переподключиться с ещё живой сессией.
- **Выход со всех устройств, смена и сброс пароля, удаление пользователя:** удалить сессии, затем
  `io.in('user:<userId>').disconnectSockets()`. Эндпоинта «выйти со всех устройств» в контракте пока нет — добавим
  отдельной задачей вместе с этим отключением.
- Через Redis-адаптер оба вызова работают на всех инстансах, как `socketsLeave` в ADR-0011.
- **Фронтенд:** после отключения сервером (`reason === 'io server disconnect'`) socket.io сам не переподключается.
  Клиент проверяет `GET /api/auth/me`: 401 — на страницу входа, 200 — подключается заново.
- **Проверить при реализации:** документация пакета не говорит, как получить id сессии при подключении сокета. Если
  его нет, при выходе отключаем `user:<userId>`: другие вкладки и устройства переподключатся сами по правилу выше,
  их сессии живы. Выходит проще, но с лишними переподключениями.
- **Известное ограничение:** у сессии, которая истекла по сроку (7 дней без активности или 30 дней с входа), нет
  события, поэтому её открытый сокет получает рассылки до переподключения. Риск меньше, чем при выходе: сессию никто
  не отзывал. Решаем отдельной задачей — например, таймер до конца срока сессии или периодическая перепроверка.
- Реализуем в задаче подключения WebSocket: gateway пока нет. Здесь записано решение.

### Контракт

Все пути с префиксом `/api`. `User` = `{ id: uuid, email, name }`.

| Запрос                | Тело                                        | Успех               | Ошибки                                     |
| --------------------- | ------------------------------------------- | ------------------- | ------------------------------------------ |
| `POST /auth/register` | `{ name (2–100), email, password (8–128) }` | 201 `User` + cookie | 400 — поля; 409 `email_taken`; 403         |
| `POST /auth/login`    | `{ email, password }`                       | 200 `User` + cookie | 400 — поля; 401 `invalid_credentials`; 403 |
| `POST /auth/logout`   | —                                           | 204 (и без сессии)  | 403                                        |
| `GET /auth/me`        | —                                           | 200 `User`          | 401 — нет сессии                           |

- **403** на любом `POST` (и на будущих `PUT`, `PATCH`, `DELETE`) — запрос пришёл не с `CORS_ORIGIN`, его отклонила
  защита от CSRF до обработчика. Для пользователя это не ошибка ввода, а неверная настройка адреса фронтенда или
  атака. Описываем 403 в контракте каждого такого эндпоинта.
- **Email** приводится к нижнему регистру.
- **На неверный email и неверный пароль ответ один** — 401 с тем же текстом, чтобы нельзя было узнать, кто
  зарегистрирован.
- **Формат ошибок — общий для всего API** (`apps/api/src/common/error.schema.ts`):
  - `ErrorResponse` = `{ statusCode, message, error?, errorCode? }` — обычное тело ошибки Nest 12;
  - `errorCode` — машинная причина ошибки из списка `ErrorCode` в OpenAPI: `validation_failed`, `email_taken`,
    `invalid_credentials`, `missing_credentials` (нет cookie сессии — код ставит сам пакет). Где кода нет (сессия
    истекла, 403, 5xx), фронтенд решает по `statusCode`;
  - для 400 от валидации — `ValidationErrorResponse` с `errors: [{ path, code, message }]`, чтобы форма показала ошибку
    у нужного поля без разбора текста; `code` — причина по Zod: `too_small`, `invalid_format` и т. п.
    (`apps/api/src/common/validation.ts`);
  - **тексты для пользователя (на русском) хранит фронтенд** и выбирает их по `errorCode` и `code`. `message` — на
    английском, для разработчика и логов: так тексты не зависят от бэкенда, а смена формулировки не меняет контракт.

## Последствия

- PR 1 (этот): ADR, контракт с ответом 501, `openapi.json` и клиент Orval — фронтенд может начинать по контракту.
  Плюс `app.enableCsrfProtection()` с e2e-тестами: она в ядре Nest и не требует пакета. Пакет
  `@nestjs/authentication` ставим в PR 2.
- Перед PR 2 — отдельная задача на подключение PostgreSQL через Drizzle ([ADR-0012](./0012-orm-drizzle.md)).
- PR 2: таблицы `users` и `sessions`, store на Drizzle, `AuthenticationModule` с глобальным guard — все эндпоинты
  закрыты, кроме помеченных `@Public()`. В `session.trustedOrigins` — тот же `CORS_ORIGIN`, что в
  `enableCsrfProtection()`. e2e: регистрация с чужого origin не создаёт пользователя.
- Фронтенду (свои задачи): форма входа — без «Запомнить меня», вместо `UserSchema` из `@app/shared` —
  сгенерированный тип `User`. **До первой формы** — задача [клиент API](../backlog/api-client.md): сейчас клиент
  Orval шлёт запросы на сам Next.js, а не на бэкенд, и не считает ответы 4xx ошибкой. Если запросы пойдут напрямую на
  `API_URL`, нужен `credentials: 'include'`, иначе браузер не отправит cookie сессии. Если через `rewrites` в Next.js
  (тот же origin) — CORS и `credentials` не нужны.
- Задача подключения WebSocket — отключение сокетов при выходе, см. [WebSocket после выхода](#websocket-после-выхода).
  Отдельными задачами: «выйти со всех устройств» и сокеты сессии, истёкшей по сроку.
- Позже, отдельными задачами: ограничение частоты входа (`@nestjs/throttler`), подтверждение email и сброс пароля (в
  пакете есть), вход через GitHub (KAN-56: GitHub — OAuth2, а не OIDC, поэтому готовый OIDC-модуль пакета не
  подходит как есть).
- Если в каком-то браузере `__Host-` cookie не ставится на `http://localhost`, для разработки включаем
  `secure: false` через переменную окружения — решим в PR 2.
