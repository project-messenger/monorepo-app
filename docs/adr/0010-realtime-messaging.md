# 0010. Обмен сообщениями в реальном времени: id от клиента, права в БД, счётчик канала

- **Статус:** принято
- **Дата:** 2026-11-20
- **Область:** api, web, shared
- **Подготовил:** ИИ-агент по запросу foxprogs; решения принял foxprogs (2026-11-20)
- **Задача:** [KAN-33](https://project-group-11.atlassian.net/browse/KAN-33)

## Контекст

ТЗ требует до основной разработки проверить на маленьком прототипе две вещи: сообщения ходят между двумя клиентами, а
после обрыва соединение восстанавливается. Требования к поведению описаны в
[docs/product.md](../product.md#сквозные-требования-к-поведению):

- сообщения не теряются, не дублируются и не меняют порядок;
- права проверяются в событиях WebSocket;
- исключённый из канала перестаёт получать его сообщения сразу;
- бэкенд работает в нескольких инстансах.

Прототип одноразовый и сделан **вне монорепы**. На момент начала основа бэкенда (KAN-13) ещё не была влита, Docker
делал другой разработчик, ORM и модель данных не были выбраны. Код в `apps/api` заставил бы принять эти решения раньше
времени и конфликтовал бы с чужими задачами. В репозиторий код прототипа не попадает, из него переносятся только выводы:
этот ADR и [события WebSocket](../backlog/socket-events.md). Стек прототипа: Node 26 (запуск `.ts` без сборки),
socket.io 4.8, `@socket.io/redis-adapter` 8.3, `pg`, Postgres и Redis в `docker-compose`.

Что проверено (скриптами на socket.io-клиенте; в браузере):

| Сценарий                                                                                              | Результат |
| ----------------------------------------------------------------------------------------------------- | --------- |
| Два клиента в одном канале получают сообщения друг друга, отправитель не получает свою копию повторно | работает  |
| Сообщение сохраняется в БД до рассылки, после перезапуска сервера история на месте                    | работает  |
| Повтор с тем же id от клиента: одна строка в БД и одно сообщение у получателя                         | работает  |
| Обрыв и переподключение: пропущенные сообщения догружаются из БД                                      | работает  |
| Два инстанса через Redis-адаптер: клиенты на разных инстансах видят друг друга                        | работает  |
| Повтор через другой инстанс возвращает то же сообщение без повторной рассылки                         | работает  |

## Варианты

### 1. Как не создать дубль при повторной отправке

1. **id выдаёт только сервер.** Если сообщение дошло, а ответ потерялся, клиент отправит его ещё раз, и сервер
   создаст второе сообщение: ему не с чем сравнить повтор.
2. **id генерирует клиент** (`crypto.randomUUID()`), в БД уникальный индекс `(user_id, client_id)`. На повтор сервер
   отвечает **успехом** и возвращает уже сохранённое сообщение. Ответ ошибкой показал бы «ошибку» у сообщения, которое
   на самом деле сохранено.

### 2. Как отправитель узнаёт, что сообщение принято

1. **Отдельное событие от сервера** «сообщение сохранено». Его приходится сопоставлять с отправкой вручную.
2. **Acknowledgement** — колбэк в `emit`, адресный ответ на одно событие одному отправителю. С
   `socket.timeout(ms).emit(...)` клиент получает ошибку, если ответа нет
   ([Acknowledgements](https://socket.io/docs/v4/emitting-events/#acknowledgements)).

### 3. Порядок сообщений и догрузка после обрыва

1. **ulid или время на сервере.** Его генерирует инстанс, поэтому при нескольких инстансах порядок зависит от их часов.
2. **Общий номер из БД** (`bigint GENERATED ALWAYS AS IDENTITY`), догрузка `WHERE id > последний`. Один источник
   номеров для всех инстансов, в прототипе этого хватило. Минус в порядке коммитов. Номер выдаётся при вставке, а
   видна строка становится после коммита:
   - транзакция A получила 101, транзакция B получила 102;
   - B закоммитилась первой, клиент получил 102 и запомнил его;
   - клиент переподключился до коммита A и запросил `id > 102`;
   - сообщение 101 он не получит никогда.

   Ещё identity тратит номер даже на повторе с `ON CONFLICT DO NOTHING`, поэтому в номерах бывают пропуски.

3. **Свой счётчик у каждого канала.** В той же транзакции, что и вставка сообщения, выполняется
   `UPDATE channels SET last_seq = last_seq + 1 WHERE id = $1 RETURNING last_seq`. Блокировка строки канала держится до
   коммита, поэтому следующая вставка в этот канал ждёт: порядок номеров совпадает с порядком коммитов. Цена: запись в
   **один** канал идёт по очереди. Сколько это стоит — замер в «Последствиях».

### 4. Как клиент узнаёт об изменениях, пропущенных офлайн

Изменение, удаление и реакции есть в любом чате. Если догрузка ищет только **новые** сообщения (`seq > последний`),
то человек, который был офлайн, не узнает, что сообщение отредактировали, удалили или на него поставили реакцию. У
него навсегда останется старая версия.

1. **Отметка времени `updated_at`**, догрузка `updated_at > последняя`. Та же проблема, что у identity: время
   ставится до коммита, и транзакция, закоммиченная позже, может получить более раннее время. Плюс при нескольких
   инстансах — разные часы. Физически удалённую строку так вообще не найти.
2. **Перезагружать последние N сообщений** при каждом подключении. Изменения старее N не придут.
3. **Connection state recovery** socket.io. Не работает с Redis-адаптером, и даже без него помогает только при
   коротком обрыве: офлайн-ночь всё равно требует догрузки из БД.
4. **Счётчик канала нумерует каждое изменение, а не только новые сообщения.** Новое сообщение, правка, удаление,
   реакция — каждое берёт следующий номер счётчика канала (3.3) в той же транзакции. Догрузка: «все изменения после
   номера X». Порядок коммитов соблюдён, ничего не теряется.

Других надёжных способов мы не нашли: нужен номер изменения, который выдаёт БД в порядке коммитов.

### 5. Где проверять права

1. **Только комнатами.** Пускаем в комнату канала при подключении и считаем, что тот, кто в комнате, имеет доступ.
   Не работает для очереди офлайн-сообщений: клиента могли исключить, пока он был офлайн, а очередь придёт в новом
   соединении. Ещё хуже, если комнату не успели обновить на другом инстансе.
2. **В БД на каждом действии.** Отправка и так пишет в БД, поэтому проверку членства можно сделать в том же запросе
   (`... WHERE EXISTS (SELECT 1 FROM channel_members ...)`): лишнего запроса не появляется. Догрузка проверяет
   членство так же.

### 6. Как вывести исключённого из комнат

1. **Поиск по префиксу** в иерархических именах комнат (`ws:<w>:proj:<p>:`). С Redis-адаптером узнать комнаты
   сокетов на всех инстансах можно только сетевым запросом (`fetchSockets()`). Кроме того, правильность зависит от
   формата имён.
2. **Список из БД.** Из БД берём каналы проекта, в которых состоял человек, и выводим его из этих комнат по именам:
   `io.in('user:<userId>').socketsLeave([...])`. Через адаптер это работает на всех инстансах. Имена комнат плоские,
   потому что id уникальны и без вложенности.

## Решение

Выбраны: id от клиента (1.2), acknowledgement (2.2), счётчик канала (3.3), который нумерует каждое изменение (4.4),
права в БД на каждом действии (5.2), список комнат из БД (6.2).

- **Источник правды — БД, комнаты только для доставки.** Комната отвечает лишь на вопрос «кому разослать». Права на
  каждое событие проверяются запросом в БД.
- **Отправка `message:send`:**
  - проверить данные Zod-схемой из `@app/shared`;
  - в одной транзакции проверить членство, увеличить `last_seq` канала и вставить сообщение;
  - если это повтор (тот же `(user_id, client_id)`), вернуть уже сохранённое сообщение;
  - только новое сообщение разослать через `socket.to('ch:<channelId>')`, то есть всем, кроме отправляющего сокета
    (другие вкладки того же человека — другие сокеты, они сообщение получат);
  - ответить ack `{ ok: true, message }` или `{ ok: false, error }`.
- **Изменения сообщения** (правка, удаление, реакция) берут номер из того же счётчика канала, в той же транзакции,
  что и само изменение. У сообщения два номера:
  - `seq` — место в ленте, выдаётся один раз при создании;
  - `changeSeq` — номер последнего изменения, обновляется при каждом изменении.

  Удаление «мягкое»: строка остаётся с отметкой удаления и без текста, иначе догрузке нечего было бы отдать.
  Хранить ли номер изменения в строке сообщения или вести отдельный журнал изменений — решается в задаче модуля
  сообщений.

- **Треды.** Ответ в треде — сообщение того же канала с `parentId`: тот же счётчик, та же комната, те же права.
  - Ответ приходит в комнату канала, но в ленте канала не показывается. Клиент показывает его в открытом треде, а под
    исходным сообщением обновляет число ответов и участников.
  - **Доставка ≠ уведомление.** Комната только обновляет экран у тех, кто смотрит канал. Уведомление об ответе
    получают подписчики треда через `user:<userId>`: автор исходного сообщения, ответившие, упомянутые. Непрочитанные
    канала ответы в треде не увеличивают. Кто подписан и как это настраивается — в задаче уведомлений.
  - Отдельную комнату `thread:<parentId>` для ответов отклонили: это ещё один тип комнат и отдельная догрузка ради
    экономии трафика, которая нам не нужна.

- **Догрузка `message:sync`:**
  - клиент вызывает её на **каждом** `connect`, по каждому открытому каналу, после последнего полученного `changeSeq`;
  - сервер отдаёт текущее состояние всех сообщений, изменённых после этого номера (новых, отредактированных,
    удалённых);
  - сервер отдаёт порцию и признак `hasMore`, клиент запрашивает дальше, пока он есть;
  - на Connection state recovery не полагаемся: Redis-адаптер его не поддерживает (таблица Supported features в README
    `@socket.io/redis-adapter`), и догрузка из БД нужна в любом случае.
- **Подключение:** всё асинхронное (кто пользователь, в каких он каналах) — в middleware `io.use()`, а не в
  `connection`. Иначе события, пришедшие сразу после подключения (очередь неотправленных), могут прийти раньше, чем
  повешены обработчики.
- **Комнаты:**
  - `ch:<channelId>` — каналы;
  - `chat:<chatId>` — групповые и личные переписки;
  - `user:<userId>` — все соединения человека: вывести из комнат, добавить в новый канал, личное уведомление;
  - `ws:<workspaceId>` и `proj:<projectId>` — для событий уровня пространства и проекта.

  Имена только из id. Разные префиксы у каналов и переписок верны при любой модели данных: и если это одна таблица,
  и если две (тогда id из разных таблиц могут совпасть).

- **Ответ ИИ стримится в комнату, а в БД пишется один раз в конце.** Куски текста во время генерации — отдельное
  событие в комнату, без записи в БД и без счётчика. Готовый ответ сохраняется одной транзакцией как обычное
  сообщение. Так генерация, которая длится секунды, не держит блокировку канала. Если понадобится, чтобы состояние
  «генерируется» переживало перезагрузку страницы, в начале вставляется черновик, а в конце он обновляется. Это тоже
  две короткие транзакции, а не одна длинная.
- **Внутри транзакции с блокировкой канала — только запросы к БД.** Вызовы ИИ, GitHub API и любые другие сетевые
  запросы делаются до или после неё.
- **Исключение из канала или проекта:**
  - удалить членство в БД;
  - вызвать `io.in('user:<userId>').socketsLeave([...])` со списком комнат из БД.

  Если человек был офлайн, при следующем подключении комнаты соберутся из БД уже без этого канала, а его очередь
  отклонит проверка прав.

- **Несколько инстансов:** адаптер socket.io через Redis (`@socket.io/redis-adapter`, два соединения: pub и sub).
- **Клиент:**
  - состояния сообщения «отправляется → отправлено / ошибка»;
  - «ошибка» означает «нет ответа за N секунд». Возможны два случая:
    - **сообщение не ушло** (не было сети). По таймауту ack socket.io удаляет событие из буфера неотправленных
      (`socket.io-client`, обработчик таймаута в `_registerAckCallback`), поэтому после переподключения оно само не
      уйдёт: нужно «повторить». Проверено в браузере;
    - **сообщение дошло, а ответ потерялся.** Оно сохранено, а ack, пришедший после таймаута, socket.io игнорирует.
      Догрузка после переподключения вернёт это сообщение и переведёт его в «отправлено»;
  - «повторить» отправляет тот же `clientId`;
  - сообщения от сервера сопоставляются по `clientId`, и уже отправленное сообщение назад в «ошибку» не переводится.

## Последствия

- Каждое действие в realtime стоит запроса в БД. Таблице членства нужен индекс по `(channel_id, user_id)`.
- Запись в один канал идёт по очереди из-за блокировки строки канала. Замер 2026-11-20: Postgres 18 в Docker на
  ноутбуке (Apple M4), пул из 20 соединений, 50 каналов. Это порядок величин, а не обещание для прода: там к каждому
  запросу добавится сеть до БД.

  | Сценарий                                                       | Сообщений/с | p50    | p95      |
  | -------------------------------------------------------------- | ----------- | ------ | -------- |
  | Общий identity, без транзакции, 1 канал, 20 параллельно        | ~15 000     | 1,2 мс | 2,1 мс   |
  | Счётчик канала, 1 канал, 20 параллельно (худший случай)        | ~1 300      | 9,8 мс | 44 мс    |
  | Счётчик канала, 50 каналов, 20 параллельно                     | ~6 100      | 3,0 мс | 5,1 мс   |
  | Догрузка 100 сообщений с проверкой прав                        | ~7 200      | 2,4 мс | 4,9 мс   |
  | Счётчик + 50 мс сетевого вызова **внутри** транзакции, 1 канал | ~18         | 870 мс | 2 900 мс |

  Даже в худшем случае канал выдерживает больше тысячи сообщений в секунду. Люди, вебхуки GitHub и ИИ дают на порядки
  меньше. Последняя строка показывает, почему внутри транзакции нельзя ходить в сеть. Если запись станет узким
  местом, транзакцию можно сократить до одного запроса (`WITH ... UPDATE ... RETURNING` + `INSERT`).

- Redis обязателен и в разработке, и в проде: его нужно добавить в [Docker](../backlog/docker.md).
- Если соединение вернулось **раньше** таймаута ack, клиент одновременно отправляет буфер и делает догрузку, а сервер
  обрабатывает их параллельно. Если догрузка выполнилась раньше сохранения, а ack не успел до таймаута, сообщение
  может остаться в «ошибке», хотя сохранено. Его поправит «повторить» (вернётся то же сообщение) или следующая
  догрузка. Дубля нет.
- Контракт событий описывается в `@app/shared` — [задача в бэклоге](../backlog/socket-events.md). Установка socket.io в
  `apps/api` и `apps/web` — после согласия команды.
- **Не решено, решать в задачах модуля сообщений:**
  - статусы «доставлено» и «прочитано» в канале и в треде;
  - хранить ли неотправленные сообщения в `localStorage`, чтобы они пережили обновление вкладки (задача фронтенда);
  - повторять ли сообщения в «ошибке» автоматически после переподключения или только кнопкой. Автоповтор безопасен:
    id от клиента не даст дубля (задача фронтенда);
  - балансировка в проде. С транспортом long-polling нужны sticky sessions, иначе можно использовать только websocket
    ([Using multiple nodes](https://socket.io/docs/v4/using-multiple-nodes/)). Зависит от того, где будем деплоить.
