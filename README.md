# Team Messenger Monorepo

Современный корпоративный мессенджер с поддержкой Kanban-задач, интеграцией с GitHub и AI-ассистентом.

Стек: **Turborepo + pnpm**, **Next.js**, **NestJS**, **PostgreSQL + Redis**, **Drizzle**, **Zod** и **Orval**.

## Предварительные требования

У вас на компьютере должны быть установлены:

- **Node.js** (версия 20+ рекомендуется)
- **pnpm** (версия 9+)
- Для PostgreSQL и Redis — **Docker Desktop** (macOS/Windows) или Docker Engine с плагином Compose (Linux).
  Нужна версия `docker compose`, поддерживающая `up --wait --wait-timeout`; Docker должен быть запущен.
  Для Docker Engine на Linux требуется версия 28.0.0 или новее: в более ранних версиях порты, опубликованные
  на `127.0.0.1`, могут быть доступны другим компьютерам той же локальной сети.

Редактор — VS Code или Cursor: при открытии проекта они предложат рекомендуемые расширения
(`.vscode/extensions.json`), а общие настройки (форматирование Prettier при сохранении, ESLint, Tailwind) подхватятся
из `.vscode/settings.json`. Личные настройки держите в пользовательских настройках редактора, а не в этих файлах.

## Настройка окружения (.env)

1. Если корневой `.env` ещё не создан, скопируйте файл-шаблон:

```bash
   cp .env.example .env
```

2. Откройте `.env` и при необходимости настройте параметры API, порты и учётные данные PostgreSQL. Если файл уже существовал, добавьте недостающие переменные из `.env.example`, сохранив свои значения. _Обратите внимание: телеметрия Turborepo в шаблоне уже отключена._

## Быстрый старт (Разработка)

1. Клонируйте репозиторий и установите зависимости **из корня проекта**:

```bash
pnpm install

```

2. Выберите вариант запуска проекта в режиме разработки (бэкенд на 3001, фронтенд на 3000).

**Без PostgreSQL и Redis:**

```bash
pnpm dev

```

**С PostgreSQL и Redis:**

```bash
pnpm infra:up
pnpm dev
```

### Полезные команды (шорткаты из корня):

- `pnpm dev:api` — запустить только NestJS бэкенд.
- `pnpm dev:web` — запустить только фронтенд.
- `pnpm build` — собрать весь проект для проверки.
- `pnpm typecheck` — проверить TypeScript во всем репозитории.
- `pnpm lint` — запустить линтер.
- `pnpm verify` — все проверки фронтенда: typecheck + lint + Prettier + тесты.
- `pnpm test:web` — unit- и компонентные тесты фронтенда (Vitest).
- `pnpm test:web:e2e` — e2e-тесты фронтенда (Playwright).
- `pnpm format:web` — отформатировать код фронтенда (Prettier).

### Локальные PostgreSQL и Redis

Конфигурация — [`docker-compose.yml`](./docker-compose.yml). Для запуска нужны работающий Docker и корневой `.env`:

```bash
pnpm infra:up       # запустить в фоне и дождаться готовности обоих сервисов
pnpm infra:status   # состояние контейнеров и результаты healthcheck
pnpm infra:logs     # последние 100 строк и новые логи; Ctrl+C завершает просмотр
pnpm infra:down     # остановить и удалить контейнеры, сохранив данные
```

Версии официальных образов зафиксированы в Compose. Причины выбора —
[ADR-0010](./docs/adr/0010-local-infrastructure.md).

API и фронтенд запускаются отдельно через существующие `pnpm dev`, `pnpm dev:api`, `pnpm dev:web`.
Подключение ORM и Redis-клиента — отдельные задачи; текущий `pnpm dev` работает без этих сервисов.

Сервисы доступны только с компьютера разработчика. Параметры подключения, загрузка `.env` и перезапуск API
после изменения настроек — в [README API](./apps/api/README.md#переменные-окружения).

Compose читает корневой `.env`; переменные терминала имеют приоритет. Если переменная отсутствует или пустая,
используется значение из Compose, совпадающее с шаблоном `.env.example`.
Внутренние порты контейнеров не меняются; при подключении с компьютера используйте выбранный внешний порт.

`POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD` задают базу и пользователя при **первом запуске с пустым
хранилищем**. Их последующее изменение в `.env` не меняет существующую базу и пароль.
Значения для подключения API или DataGrip должны совпадать со значениями в созданной базе.

Данные хранятся в именованных volumes Docker: `postgres_data` и `redis_data` (с префиксом проекта Compose).
PostgreSQL сохраняет данные в `/var/lib/postgresql`. Redis сохраняет записи в AOF в `/data`, синхронизация —
раз в секунду (`appendfsync everysec`), периодические RDB-снимки отключены. После обычной остановки и повторного
запуска данные обоих сервисов сохраняются; при аварии Redis может потерять примерно последнюю секунду записей.

**Полный сброс локальных данных:** `docker compose down --volumes` удалит volumes обоих сервисов вместе со всеми
базами и ключами. Следующий запуск создаст пустое окружение с текущими значениями `.env`.

| Проблема | Действие |
| --- | --- |
| Docker недоступен | Запустить Docker, проверить `docker info` и повторить `pnpm infra:up`. |
| Занят порт PostgreSQL или Redis | Задать свободные `POSTGRES_PORT` / `REDIS_PORT` в корневом `.env`. Если эти переменные экспортированы в терминале, также изменить их там или выполнить `unset POSTGRES_PORT REDIS_PORT`. Затем выполнить `pnpm infra:up` и перезапустить API. |
| Сервис `unhealthy` или завершился | Проверить `pnpm infra:status` и `pnpm infra:logs`, устранить причину и повторить `pnpm infra:up`. |

`infra:up` ждёт готовности до 120 секунд; ошибки загрузки образов, запуска и готовности не подавляются.

## Как работать с общим пакетом (`packages/shared`)

В папке `packages/shared` лежит то, что Swagger не описывает, а нужно обеим сторонам: события WebSocket (названия и Zod-схемы данных) и общие константы. HTTP-схемы сюда не кладём — фронтенд получает их от Orval.

- **Добавление нового события или схемы его данных:**

1. Создайте файл в `packages/shared/src/schemas/`.
2. Экспортируйте его в `packages/shared/src/index.ts`.
3. Пакеты `api` и `web` подхватят изменения автоматически.

Правила изменения пакета (в одном PR с обеими сторонами) — [packages/shared/AGENTS.md](./packages/shared/AGENTS.md).

## Как использовать Zod и Orval (Фронтенд + Бэкенд контракт)

HTTP-контракт описывает бэкенд (Zod-схемы DTO → OpenAPI), фронтенд генерирует из него клиент через Orval. Подробно —
[docs/architecture.md](./docs/architecture.md#контракт-фронтенд--бэкенд).

1. **На бэкенде (`apps/api`):**

- Вы описываете эндпоинты в NestJS с помощью `@nestjs/swagger`.
- `pnpm --filter api openapi` записывает схему в `apps/api/openapi.json` (без запуска сервера) — файл коммитится вместе с изменением эндпоинтов.

2. **На фронтенде (`apps/web`):**

- Когда бэкендеры добавляют новые эндпоинты, фронтендер может автоматически сгенерировать готовые React Query хуки и типы одной командой из `apps/api/openapi.json` (подробнее — [`apps/web/docs/tooling.md`](apps/web/docs/tooling.md#orval--клиент-api-из-swagger)):

```bash
pnpm --filter web generate-api

```

- После этого в коде фронтенда можно использовать автогенерируемые хуки с полным автодополнением (например, `useGetMessages()`).
