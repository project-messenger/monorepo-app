# Product design: командный мессенджер

> Документ описывает продуктовый интерфейс по исходному ТЗ, 19 экранам макета и отдельной странице `UI Kit / Design System` в Figma. UI Kit содержит подробную спецификацию визуальных основ и компонентов; точные значения следует сверять с этой страницей. Это рабочая спецификация для обсуждения и реализации, не финальное описание всех состояний. ТЗ задаёт обязательные возможности; решения по навигации ниже фиксируют согласованный смысл макетов; рекомендации и нерешённые вопросы помечены отдельно.

## 1. Цель продукта

Продукт — рабочий мессенджер для команд, в котором обсуждения связаны с задачами, решениями команды и изменениями в GitHub. Чат — основной сценарий; канбан, стендапы, решения и ИИ помогают команде доводить договорённости до результата.

### Главный рабочий сценарий

1. Участник обсуждает проблему в канале проекта.
2. Из сообщения создаёт задачу или создаёт задачу отдельно.
3. Задаче назначают исполнителя, статус, приоритет и срок.
4. Исполнитель связывает задачу с PR.
5. Команда получает обновления о ревью, CI и merge.
6. После завершения работы участники могут вернуться из задачи или PR к исходному обсуждению.

Каждый раздел должен поддерживать этот путь. Чат, задачи, GitHub и уведомления не должны выглядеть как несвязанные самостоятельные продукты.

### Приоритеты продукта из ТЗ

**Сначала основной сценарий:** аутентификация, пространство, приглашение второго участника, проект и канал, обмен сообщениями, создание задачи из обсуждения, переход задачи в готовое состояние.

**Следующим этапом:** GitHub, стендапы, решения команды и ИИ. Уведомления и личный кабинет описаны в ТЗ как функциональные требования; интеграции и расширенные настройки можно выпускать поэтапно.

**Дополнительное задание:** голосовые комнаты. Их отсутствие не блокирует завершение основного продукта.

## 2. Продуктовая модель и термины

### Рабочее пространство

Рабочее пространство объединяет участников, проекты, каналы, личные сообщения и общие настройки. Пользователь может состоять в нескольких пространствах.

В макетах пример пространства называется **Orbital**. В текущем логотипе показано **«СИНК /»**. Это имена-примеры из прототипа; окончательное название продукта и бренд-система не зафиксированы.

### Проект

Проект создаётся внутри рабочего пространства. Он объединяет описание, участников, каналы, канбан-доску, стендапы, решения и GitHub-репозиторий. Примеры в макетах: **Веб-платформа** и **Мобильное приложение**.

### Канал

Канал принадлежит проекту и содержит сообщения команды. Канал может быть открытым для участников проекта или закрытым с отдельным списком приглашённых участников.

### Задача

Задача принадлежит проекту. Она может быть создана из сообщения или независимо от чата. Если задача создана из сообщения, нужно сохранить ссылку на исходное обсуждение. У задачи есть отдельная ветка обсуждения, доступная из карточки задачи и из канала.

### Решение команды

Зафиксированная договорённость или техническое решение с контекстом, автором, датой, историей изменений и ссылкой на обсуждение. Решение отличается от задачи: оно сохраняет «что решили и почему», задача — «что нужно сделать».

## 3. Роли и доступ

ТЗ требует минимум три роли пространства: **владелец**, **администратор**, **участник**. Точная матрица разрешений для создания проектов, приглашений и управления каналами в ТЗ оставлена команде на определение.

### Обязательные правила доступа

- В открытый канал могут входить участники проекта.
- В закрытый канал — только приглашённые пользователи.
- Приглашённый участник закрытого канала видит канал в навигации и может читать переписку.
- Неприглашённый пользователь не видит содержимое закрытого канала; права должны проверяться в поиске, файлах, ИИ и realtime-событиях.
- Удалённый участник закрытого канала не должен получать новые сообщения через ранее открытое соединение.
- Подключение приватного GitHub-репозитория не открывает его данные всему пространству автоматически.
- Доступ к задаче и прикреплённому файлу должен проверяться независимо от наличия ссылки.

### Отделять управление от чтения

Экран управления каналами может показывать администратору названия, тип и состав каналов для администрирования. Это само по себе не должно предоставлять доступ к сообщениям закрытого канала. Интерфейс обязан ясно разделять действия **«настроить канал»** и **«открыть переписку»**.

## 4. Информационная архитектура

### Общая оболочка приложения

После входа пользователь попадает в выбранное рабочее пространство. Общая оболочка содержит:

- сайдбар с личными разделами, проектами, каналами, личными сообщениями и настройками пространства;
- верхнюю шапку с глобальным поиском и ссылкой на помощь;
- область контента текущего экрана;
- меню личного профиля.

Индикатор **«В сети»** текущего пользователя в шапке прототипа не даёт полезного контекста, если человек уже работает в приложении. Рекомендация: убрать его из постоянной шапки, а присутствие показывать рядом с участниками, сообщениями и списком личных переписок. Присутствие других пользователей и точность статуса в нескольких вкладках остаются обязательными требованиями ТЗ.

### Сайдбар

Порядок и назначение разделов:

1. **Переключатель пространства** — меняет активное пространство.
2. **Моя работа** — личная сводка по всем проектам: назначенные задачи, запросы на проверку, упоминания.
3. **Уведомления** — единый центр переходов к сообщениям, задачам, PR и другим событиям.
4. **ИИ-помощник** — общий вход в ИИ; открытие из проекта подставляет контекст этого проекта.
5. **Поиск** — переход к полной странице поиска с фильтрами. Поле в шапке служит быстрым поиском и после подтверждения запроса открывает эту же страницу с результатами. Это два входа в один поиск, а не два независимых поиска.
6. **Проекты** — список проектов текущего пространства. Раскрытый проект показывает только каналы и инструменты, доступные этому пользователю.
7. **Личные сообщения** — личные и групповые переписки со счётчиками непрочитанного.
8. **Участники / Настройки** — управление пространством, отдельно от личного профиля.
9. **Профиль пользователя** — переход к личным настройкам и действиям аккаунта.

Закрытый канал показывается в сайдбаре участнику, которому разрешён доступ. Он скрыт для остальных пользователей. Это обязательное согласование состояний между экраном управления каналами и навигацией.

### Хлебные крошки

Хлебные крошки должны отражать реальный путь и область настроек. Предлагаемый формат:

- проектная страница: `Orbital / Веб-платформа / Доска задач`;
- настройки каналов проекта: `Orbital / Веб-платформа / Настройки проекта / Каналы`;
- управление участниками: `Orbital / Участники`;
- личные настройки: `Анна Смирнова / Личные настройки`.

## 6. Спецификация экранов

### 01. Лендинг

**Задача экрана:** объяснить продукт как единый рабочий контекст для чатов, задач и GitHub, привести пользователя к первому действию.

**На макете:** навигация по продукту/команде/безопасности, вход и создание пространства; основное обещание «От “обсудим” до “готово”. Вместе.»; пример канала с сообщением, связанной задачей и PR; объяснение шагов продукта; явный акцент на контроле доступа.

**Переходы:** `Войти` → 03; `Создать пространство` или `Начать с командой` → регистрация/вход, затем 04. Точный сценарий для незалогиненного пользователя следует унифицировать: регистрация аккаунта и создание пространства — разные шаги.

### 02. Регистрация

**Задача экрана:** создать аккаунт пользователя. Поля макета: имя, рабочая почта, пароль; также предлагается продолжить с GitHub.

**Переходы:** существующий аккаунт → 03; успешная регистрация → создание пространства 04 или принятие приглашения, если пользователь пришёл по invite link.

**Состояния, которые нужны для реализации:** ошибки полей, занятая почта, требования к паролю, обработка GitHub OAuth, загрузка и ошибка отправки формы, подтверждение почты при необходимости. Эти состояния не прорисованы полностью.

### 03. Вход и восстановление доступа

**Задача экрана:** войти существующей учётной записью или восстановить доступ. Макет содержит вход по почте/паролю и через GitHub, ссылку «Забыли пароль?» и подсказку «Не получается войти?».

**Переходы:** регистрация → 02; успешный вход → последнее/приглашённое рабочее пространство; восстановление пароля → отдельный шаг ввода почты и подтверждения.

### 04. Создание рабочего пространства

**Задача экрана:** создать первое пространство и пригласить коллег. Макет показывает шаги онбординга, имя пространства, адрес/slug, проверку доступности, роль владельца и действие приглашения.

**Успешный результат:** пространство создано, пользователь становится владельцем, приглашения отправлены или пропущены; далее предлагается создать первый проект.

**Уточнить:** на макете основная кнопка совмещает создание пространства и приглашение. Следует определить, создаётся ли пространство до отправки приглашений, можно ли пропустить приглашение и как пользователь возвращается после ошибки адреса.

### 05. Участники и приглашения

**Задача экрана:** управлять составом рабочего пространства. Макет включает адрес приглашённого, выбор роли, отправку, вкладки участников/приглашений, присутствие, смену ролей, удаление и отзыв приглашения; поясняется область ответственности владельца и администраторов.

**Правила:** владельца нельзя случайно удалить обычным действием; изменение роли должно отображать итоговые права; приглашение имеет статус и срок; отзыв убирает возможность принять приглашение. Точные полномочия ролей следует согласовать.

### 06. Создание проекта

**Задача экрана:** создать проект внутри пространства. Форма содержит название, описание, участников и видимость; справа показан блок стартовых элементов: канал, канбан и контекст команды.

**Рекомендация:** определить один сценарий. Для создания нового проекта показывать путь `Orbital / Новый проект`, пустые поля и не выделять существующий проект. Если это онбординг первого проекта — не показывать заранее заведённые проекты в сайдбаре.

### 07. Канал и обсуждение

**Задача экрана:** основной чат проекта. Макет показывает вкладки обсуждения/закреплённого/файлов, состояние соединения, дату и непрочитанные сообщения, сообщение с вложением, реакциями, счётчиком ответов и связанной задачей, событие GitHub, поле ввода; справа открыта ветка.

**Принцип:** канал читается как чат. Постоянно видны сообщения и компактные ссылки на вложения, задачу, PR и ветку. Подробные действия сообщения группируются в меню или показываются при наведении. События GitHub должны визуально отличаться от пользовательских сообщений, но оставаться частью ленты.

**Ветки:** под исходным сообщением показывается количество/превью ответов. Нажатие открывает отдельный чат ветки (в боковой панели или ином согласованном режиме) с контекстом исходного сообщения. Панель не должна чрезмерно сжимать канал.

**Состояния:** сообщение может быть отправлено, отправляется или завершилось ошибкой; ошибка даёт повторную отправку без дубля. В макете «Возьму проверку · Не отправлено» неясно, является ли это сообщением или действием над PR. Текст и повтор должны называть конкретное неудавшееся действие.

### 08. Управление каналами

**Задача экрана:** управлять каналами проекта, включая открытые и закрытые, архив и состав участников.

**Вход:** пункт `···`(или в настройках проекта) у проекта → `Управление каналами` . Отдельного пункта в текущем сайдбаре нет; необходимо добавить явный маршрут.

**Закрытый канал:** участник закрытого канала должен видеть его в своём сайдбаре. На экране управления каналом «Безопасность» показан как закрытый с тремя участниками; это согласуется с интерфейсом только если текущий пользователь входит в эти три участника. Пользователь без членства не должен видеть переписку; административный доступ к настройкам сам по себе не открывает сообщения.

### 09. Создание задачи

**Задача экрана:** создать задачу отдельно или из выбранного сообщения. Поля макета: название, описание, чеклист, файлы и связанные сообщения, исполнитель, статус, приоритет, срок, автор, отметка блокировки.

**Навигация:** сайдбар `Доска задач` открывает канбан 10. Создание задачи — отдельное действие с доски или сообщения; форма может открываться модальным окном/панелью, сохраняя контекст. Если используется отдельная страница, активный пункт и хлебные крошки должны отражать `Создание задачи`, а не выдавать её за доску.

**Связь с обсуждением:** для задачи, созданной из сообщения, сохранить источник и открыть её обсуждение из карточки и канала. Для задачи «без исходного сообщения» нельзя обещать доступ к ветке из канала `#разработка`, пока пользователь явно не связал задачу с сообщением/каналом. На макете эту сноску нужно переписать или ограничить задачами, созданными из обсуждения.

### 10. Канбан проекта

**Задача экрана:** открыть доску проекта. Колонки макета: «Нужно сделать», «В работе», «На проверке», «Готово»; карточки показывают ID, название, приоритет, исполнителя и срок. Есть фильтры по исполнителю, приоритету и сроку, настройка колонок, создание задачи.

**Поведение:** перетаскивание меняет статус/порядок и синхронизируется в реальном времени. Ошибка изменения должна восстанавливать актуальное состояние и позволять повторить действие. Параллельные изменения не должны терять карточки. В ТЗ можно настраивать колонки; сложные Jira workflow и спринты не требуются.

**Переходы:** клик по карточке → 11; `Создать задачу` → 09; связанные сообщения или обсуждение из карточки ведут в соответствующий канал/ветку.

### 11. Карточка задачи

**Задача экрана:** показать полное состояние задачи: описание, чеклист, PR, файлы/сообщения, обсуждение и историю изменений. Макет демонстрирует статус, исполнителя, автора, приоритет, срок, блокировку и ленту последних изменений.

**Обязательные данные по ТЗ:** идентификатор, название, описание, исполнитель, автор, статус, приоритет, срок и чеклист. Поддерживаются связанные файлы и сообщения, задача из PR и переход к исходной переписке.

**Действия:** менять статус/поля, отметить блокировку и указать причину, открыть связанный PR, перейти к обсуждению. Изменение статуса, срока, описания или исполнителя фиксируется в истории с автором. Статусы синхронизируются с канбаном и GitHub-правилами.

### 12. Моя работа

**Задача экрана:** персональный обзор задач из всех проектов. Макет включает счётчики задач/запросов на проверку/упоминаний, фильтры или вкладки, таблицу задач с проектом, статусом и сроком, отдельный блок PR на проверку и блок упоминаний.

Это глобальная личная страница, а не список задач только текущего проекта. Клик ведёт к задаче, PR или сообщению в исходном проекте. Счётчики должны объяснять, что включено в число, и согласовываться с фактическим списком.

### 13. GitHub

**Задача экрана:** управлять интеграцией GitHub проекта. Макет показывает репозиторий `orbital/web`, подключившего пользователя, канал событий, категории уведомлений, правила связи PR и задач, последние события и состояние доступа.

**Правила из ТЗ:** для первой версии один репозиторий на проект; репозиторий подключает пользователь с нужными правами; секреты не попадают во frontend или сообщения; проверяется подлинность webhook; повторная доставка webhook идемпотентна; приватная информация доступна только тем, кому разрешено.

Правила вида `PR открыт → На проверке` и `PR влит → Готово` видны в истории задачи. Нужно определить поведение при нескольких PR у одной задачи и показывать успешное/ошибочное подключение и расширение доступа.

### 14. Стендапы

**Задача экрана:** асинхронно собрать отчёты команды. Макет показывает расписание и часовой пояс, число ответивших, личный опубликованный ответ, ответы команды, историю по датам и ИИ-сводку с источниками. Можно добавить задачу или PR к ответу.

**Правила из ТЗ:** администратор проекта задаёт расписание, пояс и вопросы; система напоминает участникам; ответы за день собраны в одном обсуждении; видны ответившие и ожидаемые; история доступна участникам проекта; ИИ суммирует прогресс, блокировки и кому нужна помощь, с ссылками на ответы.

Telegram может доставлять напоминания, если подключён и выбран пользователем. Сводка должна показывать состояние генерации/ошибку и обновление, а не выглядеть как неподтверждённая истина.

### 15. Решения команды

**Задача экрана:** хранить договорённости с контекстом и историей. Макет показывает списки всех/действующих/архивных решений, ID ADR, версию, автора/дату, обоснование, исходное обсуждение, связанные задачи и историю замены.

Решение можно сохранить из сообщения или ветки. Замена создаёт новую действующую версию, сохраняет предыдущую и причину. ИИ может предложить черновик; участник проверяет и сохраняет его самостоятельно. «Архив» и формат ADR — решения прототипа, не прямые требования ТЗ.

### 16. ИИ-помощник

**Задача экрана:** отвечать на вопросы по рабочему контексту проекта, а не быть общим чат-ботом. Макет показывает выбранный проект, ответ с цитируемыми источниками, предупреждение при недостаточном контексте и карточки задач/решений, которые можно создать или открыть.

ИИ может пересказывать пропущенные обсуждения, отвечать по доступным сообщениям/задачам/решениям, предлагать задачи, делать сводку проекта и черновик еженедельного отчёта. Ответы содержат ссылки к источникам. Недостаток данных обозначается явно.

Действия ИИ не изменяют данные без подтверждения. Контекст проекта виден и изменяем. Запросы подчиняются тем же правам, что и прямой доступ к каналам, задачам, репозиториям и файлам.

### 17. Поиск

**Задача экрана:** найти сведения в переписке и рабочем контексте. Макет показывает строку запроса, фильтры проекта, канала, автора и даты, категории результатов и переходы к сообщениям.

В ТЗ явно требуется поиск по сообщениям с указанными фильтрами. Другие типы результатов (задачи, решения, PR) допустимы, если для них определён понятный тип и права доступа. Результат должен показывать автора, дату, канал/проект и совпавший контекст; открывать исходный объект. Поиск не должен раскрывать закрытый канал.

Поле поиска в шапке — быстрый вход; Enter ведёт на этот экран с запросом и фильтрами. Пункт `Поиск` в сайдбаре открывает полный экран без запроса.

### 18. Уведомления

**Задача экрана:** единый центр событий. Макет содержит категории упоминаний, задач, ревью и решений, действия прочитать всё, временные метки и карточки событий; справа — настройки приоритетов и Telegram.

ТЗ требует уведомления об упоминаниях, назначении задач, ответах в обсуждениях, запросах ревью и переходы к конкретным источникам. Настройки задаются на уровне проекта/канала, есть рабочие часы и режим «Не беспокоить». Прочтение синхронизируется между вкладками. Telegram поддерживает указанные в ТЗ типы напоминаний/событий.

В макете уведомления должны быть однозначно классифицированы (например, задача заблокирована, запрос ревью, ответ в ветке) и содержать ссылку к источнику. Доставка и состояние прочтения — разные свойства.

### 19. Личные настройки

**Задача экрана:** управлять личным профилем и предпочтениями. Макет включает вкладки профиля, уведомлений, безопасности и подключений; профиль и почту; часовой пояс, рабочие дни/часы и DND; доставку по проектам/каналам; подключённый Telegram-бот и типы сообщений.

**Маршрут:** меню профиля пользователя → `Личные настройки`. Нижний пункт `Настройки` в сайдбаре следует трактовать как настройки пространства; нельзя вести им в личные настройки без явной подписи.

Пользователь выбирает каналы доставки и виды уведомлений. Telegram не повторяет прочитанное и учитывает DND/рабочее время. Сохранение подтверждается и должно иметь состояние ошибки.

## 7. Сквозные пользовательские потоки

### Первый запуск

`Лендинг → регистрация/вход → создание пространства → приглашение коллег → создание проекта → создание/открытие канала → обмен сообщениями`.

Нельзя показывать в сайдбаре проекты, которых ещё нет, одновременно с формой создания первого проекта. После регистрации по приглашению следует вести в пространство, по которому пришло приглашение, а не обязательно в создание нового пространства.

### Сообщение → задача → PR → готово

`Сообщение в канале → Создать задачу → назначить исполнителя/срок → задача появляется в канбане → связать PR → PR открыт / ревью / CI / merge → автоматический статус и событие → из задачи перейти к исходной ветке`.

При создании из сообщения сохраняются исходное сообщение и канал. При создании отдельно связь не появляется автоматически. Задача, созданная из сообщения, имеет обсуждение, доступное из карточки и канала согласно правам.

### Управление закрытым каналом

`Проектное меню → Управление каналами → создать/изменить закрытый канал → пригласить участников → канал появляется в сайдбаре приглашённых → переписка доступна только членам канала`.

Удаление из канала отзывает дальнейший realtime-доступ и доступ к сообщениям/файлам по правилам продукта.

### Ветка обсуждения

`Канал → сообщение со счётчиком ответов → открыть ветку → ответить / приложить файл / сослаться на задачу → открыть ту же ветку из связанной карточки задачи`.

## 8. Состояния и взаимодействия

### Сообщения и соединение

- real-time доставка; история хранится на сервере;
- курсор/пагинация истории при прокрутке вверх;
- новое сообщение не перебрасывает пользователя вниз, если тот читает историю;
- состояния отправки: отправляется, отправлено, ошибка;
- повтор отправки не создаёт дубль;
- восстановление соединения догружает пропущенные сообщения и показывает синхронизацию;
- редактирование собственного сообщения помечается; пользователь может редактировать и удалять свои сообщения;
- наличие ответа в ветке, реакций, упоминаний и первого непрочитанного видно отдельно.

### Задачи и доска

- изменения показываются актуально, ошибка даёт возможность повторить;
- drag-and-drop сохраняет порядок задач;
- конкурирующие перемещения нескольких пользователей не теряют карточки;
- блокировка имеет причину и видна ответственному;
- история показывает кто и что изменил;
- PR-автоматизация идемпотентна и объяснима в истории.

### ИИ

Для запросов показываются состояния выполнения, завершения и ошибки. Ответ позволяет проверить источники. ИИ сообщает, если данных недостаточно, и не выполняет внешние действия без подтверждения.

### Формы

Формы показывают обязательность полей, ошибки валидации, ожидание отправки, успешное сохранение и возможность исправить/повторить ошибочное действие. При создании объекта из другого контекста исходные связи не теряются.

## 9. Визуальное направление и UI

Прототип задаёт начальное направление: светлый рабочий фон, тёмно-зелёный сайдбар, зелёные акценты, бледно-зелёные информационные поверхности, скруглённые карточки и сдержанная типографика. Цвета/радиусы — отправная точка общего макета, не формальная бренд-система.

Указанный стек UI: **shadcn/ui + Tailwind CSS**. Компоненты интерфейса должны собираться из повторяемых паттернов (кнопки, поля, меню, вкладки, карточки, таблицы, диалоги, уведомления), с минимумом разрозненных локальных стилей. Макет сам по себе не гарантирует соответствие конкретным shadcn-компонентам; компоненты и токены следует согласовать при реализации.

### Визуальная иерархия

- главный объект экрана получает ясный заголовок и ожидаемую ширину;
- действия создания отделены от обзора/списка;
- вторичные метаданные тише основного содержания;
- карточки имеют достаточные внутренние отступы и видимое различие от фона;
- активный пункт навигации совпадает с фактическим экраном;
- закрытые состояния, ошибки и блокировки имеют текстовое объяснение, не только цвет.

### UI Kit / Design System и передача в код

Figma-файл разделён на две страницы: основная страница с 19 экранами продукта и отдельная страница `UI Kit / Design System`. UI Kit подробно описывает визуальные основы и повторно используемые элементы, необходимые для завершения макета и дальнейшей реализации: цветовые и текстовые стили, размерности и радиусы, компоненты, их варианты и состояния. Точные значения и состав компонентов являются частью Figma-страницы UI Kit; этот документ не дублирует их вручную, чтобы не создавать расходящиеся копии.

Для последующей генерации и адаптации интерфейса через Figma MCP следует использовать именованные переменные и стили для токенов, а также редактируемые компоненты с ясными названиями вариантов, размеров и состояний. Перед генерацией кода нужно сопоставить эти значения с дизайн-системой репозитория. MCP может использовать контекст экранов и UI Kit для подготовки кода, но сгенерированный интерфейс необходимо проверить на соответствие существующим компонентам, поведению, адаптивности и требованиям доступности.

В кодовой базе уже есть базовый UI: Inter, Tailwind CSS v4 и shadcn `base-nova` на Base UI; CSS-переменные задают семантические цвета и радиусы, а кнопки имеют варианты и размеры. Текущие цвета в коде нейтральные и не подтверждают автоматически палитру макета. Поэтому UI Kit следует считать описанием визуального решения в Figma, а совпадение с кодовыми токенами и компонентами — отдельной задачей сверки перед переносом. Не считать соответствие проверенным только на основании наличия UI Kit или MCP.

## 11. Область первой версии

Рекомендация по порядку проектирования и реализации в соответствии с ТЗ:

1. Аутентификация, создание пространства, участники и роли.
2. Проект, каналы и приватность.
3. Надёжный чат, история, ветки, файлы, реакции, упоминания и непрочитанное.
4. Создание задачи из сообщения, карточка задачи и канбан.
5. Полный цикл задачи с PR, уведомлением и возвратом к исходному обсуждению.
6. Моя работа, уведомления и поиск.
7. Стендапы, решения и ИИ с проверяемыми источниками.
8. Расширенные уведомления и Telegram.
9. Голосовые комнаты — необязательно.

Это порядок разработки, а не утверждённое ограничение интерфейса. Подробный roadmap команда согласует отдельно.

## 12. Что не входит в цель продукта

- Полная замена Jira с крупными workflow, спринтами, учётом времени и множеством отчётов.
- ИИ, который без проверки меняет задачи, публикует решения или отправляет сообщения.
- Автоматическое раскрытие приватного содержимого всем участникам пространства.
- Голосовые комнаты как блокирующее требование релиза.

## 13. Технический контекст для дизайна

Интерфейс должен поддерживать указанный ТЗ стек: Next.js, TypeScript, TanStack Query, Zustand, shadcn/ui, Tailwind CSS, React Hook Form, Zod, Socket.IO и библиотеку drag-and-drop. Для UI-компонентов предполагается Storybook.

Дизайн должен предусмотреть:

- раздельное состояние серверных данных, локального интерфейса и соединения Socket.IO;
- загрузку больших историй сообщений без блокировки интерфейса;
- оптимистичные/конкурирующие операции с откатом или повтором при ошибке;
- realtime обновления статусов задач, присутствия, непрочитанного и уведомлений;
- валидацию форм на клиенте и отображение ошибок сервера;
- доступность с клавиатуры и видимые фокус/ошибку/disabled-состояния компонентов.

Этот раздел фиксирует ограничения интерфейса, но не заменяет архитектурную документацию кода.

## 14. Открытые вопросы для команды

1. Матрица ролей: кто создаёт проекты, приглашает участников, создаёт/архивирует каналы и меняет роли?
2. Видимость проекта: что именно ограничивает «закрытый проект» и как это соотносится с членством пространства?
3. Создаётся ли при новом проекте стартовый канал и доска автоматически?
4. Какой UI открывает ветку: боковая панель, расширенный чат или отдельный route?
5. У задачи, созданной отдельно, есть отдельная ветка обсуждения; откуда пользователь может её открыть, если она не связана с сообщением?
6. Как показывать администратору закрытый канал, если он не участник: скрыть полностью, показать метаданные или разрешать административный просмотр содержимого?
7. Является ли Telegram первой версией или последующим этапом?
8. Какие типы объектов входят в глобальный поиск кроме сообщений?
9. Как определяется active/current project для ИИ при переходе из личного раздела или страницы пространства?
10. Какие значения и компоненты из Figma UI Kit утверждены как официальные для продукта, и какие из них уже сверены с токенами и компонентами репозитория?
