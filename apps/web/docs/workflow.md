# Процесс работы

[← к README](../README.md)

## Trunk-based development

Есть одна основная ветка — `main` (trunk). Все работают в **коротких ветках** от неё и возвращаются через PR
как можно быстрее — за день-два, а не за неделю. Чем меньше PR, тем быстрее ревью и меньше конфликтов.

Незаконченную фичу можно вливать, если она скрыта от пользователя (не подключена к роуту или выключена флагом).

## Что настроено в репозитории

На `main` действуют правила (ruleset «Main» в настройках GitHub):

- напрямую в `main` пушить нельзя — только через PR;
- нужен **1 approve**, и все обсуждения в PR должны быть закрыты;
- новый push сбрасывает approve — ревьюер смотрит актуальную версию;
- только **squash merge**: весь PR становится одним коммитом в `main`;
- удалить `main` и переписать его историю (force-push) нельзя.

## Шаги

```bash
git switch main && git pull
git switch -c feat/web-message-list          # 1. ветка от свежего main

# ... код, тесты ...

pnpm typecheck && pnpm lint && pnpm build    # 2. то же, что CI
pnpm --filter web test

git add <файлы> && git commit -m "feat(web): add virtualized message list"   # 3. коммит
git fetch && git rebase origin/main          # 4. подтянуть свежий main
git push -u origin feat/web-message-list     # 5. пуш
gh pr create                                 # 6. PR
```

После merge удалите ветку — автоудаление в репозитории выключено.

## Имена веток и коммитов

Коммиты и заголовки PR — в стиле [Conventional Commits](https://www.conventionalcommits.org/ru/):
`тип(область): что сделано`.

| Тип        | Когда                             |
| ---------- | --------------------------------- |
| `feat`     | новая возможность                 |
| `fix`      | исправление ошибки                |
| `refactor` | переделка без изменения поведения |
| `test`     | только тесты                      |
| `docs`     | только документация               |
| `chore`    | зависимости, конфиги              |
| `ci`       | GitHub Actions                    |

Область для фронтенда — `web`: `feat(web): add kanban board drag-and-drop`.
Так как PR сливается squash'ем, **заголовок PR и станет коммитом в `main`** — пишите его так же.

Ветки — `тип/web-кратко`: `feat/web-message-list`, `fix/web-scroll-jump`.

## Чек-лист перед PR

- [ ] Ветка от свежего `main`, PR про одну задачу.
- [ ] `pnpm typecheck && pnpm lint && pnpm build` проходят.
- [ ] Новая логика покрыта тестами, `pnpm --filter web test` проходит.
- [ ] Новый UI-компонент — с story.
- [ ] Добавили пакет — объяснили в описании PR, зачем, и закоммитили `pnpm-lock.yaml`.
- [ ] Нет секретов и `.env` в коммите.
- [ ] Обновили документацию, если поменяли то, что в ней описано.

## Ревью

ТЗ требует перекрёстное ревью — не только тимлид. На ревью смотрим:

- соблюдены ли слои FSD (steiger ловит не всё — например, логику в `shared`);
- где лежит состояние (см. [Состояние и данные](./state-and-data.md));
- используются ли компоненты `shared/ui` и токены темы, а не свои стили;
- есть ли тесты на новую логику.
