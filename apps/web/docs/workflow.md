# Процесс работы

[← к README](../README.md)

Правила общие для всей монорепы (frontend, backend, общие пакеты). Исходный документ команды — «Правила работы с Git» в Confluence; он ещё на обсуждении, поэтому здесь описаны только согласованные правила.

## Trunk-based development

Есть одна основная ветка — `main` (trunk). Отдельной постоянной ветки `develop` нет. Все работают в **коротких временных ветках** от `main` и возвращаются через PR как можно быстрее. Чем меньше PR, тем быстрее ревью и меньше конфликтов.

Ориентир — **до трёх дней** от создания ветки до попадания в `main`; в этот срок входят разработка, ожидание ревью, исправления и одобрение. Срок учитывает разные часовые пояса участников. Небольшие изменения можно сливать раньше. Срок не отменяет требований к качеству: ревью и обязательные проверки нужны всегда.

Незаконченную фичу можно вливать, если она скрыта от пользователя (не подключена к роуту или выключена флагом).

## Что настроено в репозитории

На `main` действуют правила (ruleset «Main» в настройках GitHub):

- напрямую в `main` пушить нельзя — только через PR;
- нужен **1 approve** от другого участника, и все обсуждения в PR должны быть закрыты;
- новый push сбрасывает approve — ревьюер смотрит актуальную версию;
- только **squash merge**: весь PR становится одним коммитом в `main`;
- удалить `main` и переписать его историю (force-push) нельзя.

## Шаги

1. Выберите задачу в Jira и уточните ожидаемый результат.
2. Создайте ветку от свежего `main`.
3. Делайте работу небольшими коммитами.
4. Откройте PR в `main`.
5. Другой участник проводит ревью, CI проверяет изменения.
6. Внесите исправления в ту же ветку.
7. После approve и зелёного CI — **Squash and merge**, затем удалите ветку.

```bash
git switch main && git pull
git switch -c KAN-7/add-message-list          # 1. ветка от свежего main

# ... код, тесты ...

pnpm typecheck && pnpm lint && pnpm build     # 2. то же, что CI
pnpm --filter web verify                       #    плюс Prettier и тесты

git add <файлы> && git commit -m "feat: KAN-7 add virtualized message list"   # 3. коммит
git push -u origin KAN-7/add-message-list     # 4. пуш
gh pr create                                  # 5. PR
```

После merge удалите ветку — автоудаление в репозитории выключено. Для следующей задачи создайте новую ветку от актуального `main`.

## Обновление рабочей ветки

Если за время работы в `main` появились изменения, **влейте `main` в свою ветку** (merge, не rebase):

```bash
git fetch
git merge origin/main
```

Разрешите конфликты и проверьте, что приложение работает. Если PR уже открыт — убедитесь, что CI зелёный на обновлённой версии. Служебный merge-коммит можно оставить со стандартным сообщением Git: формат из раздела ниже на него не распространяется.

## Имена веток

Формат: `<ключ-задачи-Jira>/<краткое-описание>`.

```
KAN-7/setup-frontend
KAN-21/add-message-list
```

- Ключ задачи — полностью и с сохранением регистра (`KAN-7`).
- Ключ и описание разделяются `/`.
- Описание — на английском, строчными буквами, слова через дефис.
- Описание отражает суть работы.

Формат один для frontend, backend и общих пакетов.

## Сообщения коммитов

Основа — [Conventional Commits](https://www.conventionalcommits.org/ru/) с **обязательным ключом задачи Jira**.

Формат: `<тип>: <ключ-задачи-Jira> <описание изменения>`.

```
chore: KAN-7 set up frontend application
build: KAN-7 configure TypeScript
docs: KAN-7 add frontend startup instructions
```

| Тип        | Когда                                                  |
| ---------- | ------------------------------------------------------ |
| `feat`     | новая функциональность или расширение существующей     |
| `fix`      | исправление ошибки                                     |
| `docs`     | только документация                                    |
| `style`    | форматирование кода без изменения поведения            |
| `refactor` | изменение структуры кода без изменения поведения       |
| `perf`     | улучшение производительности                           |
| `test`     | добавление или исправление тестов                      |
| `build`    | система сборки, настройка зависимостей                 |
| `ci`       | автоматические проверки и CI/CD                        |
| `chore`    | прочие технические изменения, например настройка Husky |

Правила написания:

- Тип — строчными буквами, после него двоеточие и пробел.
- Ключ Jira — полностью, с сохранением регистра.
- Описание — на английском, в повелительной форме: `add validation`, а не `added validation` и не `adds validation`.
- Описание называет конкретное изменение. Формулировки `update code`, `changes`, `fix stuff` не используются.
- Скоупа в скобках (`feat(web):`) в формате нет.

Один коммит — одно логически связанное изменение. Независимые изменения с разными целями оформляйте отдельными коммитами. В одной ветке допустимы коммиты разных типов; их количество не ограничено.

> Пока формат коммитов нигде не проверяется автоматически (commitlint в репозитории нет) — следите за ним сами.

## Pull Request

**Заголовок** описывает результат всего PR и пишется в том же формате, что и коммит: `<тип>: <ключ-задачи-Jira> <краткое-описание>`. Ключ совпадает с ключом в имени ветки. Так как PR сливается squash'ем, **заголовок PR станет коммитом в `main`** — проверьте его перед слиянием.

**Описание** состоит из трёх разделов:

| Раздел             | Содержание                                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Задача**         | Ссылка на задачу в Jira                                                                                                                                     |
| **Что изменилось** | Цель и результат. Если затронуты несколько частей монорепы — изменения по каждой из них                                                                     |
| **Проверка**       | Какие проверки выполнил автор и каков результат. При необходимости — шаги для ручной проверки и доп. действия (зависимости, переменные окружения, миграции) |

При изменении внешнего вида интерфейса приложите скриншот.

Заготовка описания:

```md
## Задача

[KAN-7](<ссылка на задачу>)

## Что изменилось

<Кратко: цель и результат изменения.>

## Проверка

- <Выполненная проверка и её результат.>
- <При необходимости — шаги для ручной проверки.>
```

## Чек-лист перед PR

- [ ] Ветка от свежего `main`, PR про одну задачу, имя ветки и заголовок PR с ключом Jira.
- [ ] `pnpm typecheck && pnpm lint && pnpm build` проходят.
- [ ] `pnpm --filter web verify` проходит (typecheck, lint, Prettier, тесты).
- [ ] Новая логика покрыта тестами.
- [ ] Новый UI-компонент — с story.
- [ ] Добавили пакет — объяснили в описании PR, зачем, и закоммитили `pnpm-lock.yaml`.
- [ ] Нет секретов и `.env` в коммите.
- [ ] Обновили документацию, если поменяли то, что в ней описано.

## Ревью

Каждый PR в `main` проверяет другой участник команды. Ревью **перекрёстное**: проверяем друг друга, в том числе за пределами своей обычной зоны, если можем оценить изменения. Это не обязанность одного тимлида.

**Автор:** просматривает свои изменения, сверяет их с задачей Jira, заполняет описание и запрашивает ревью у того, кто может оценить затронутый код.

**Ревьюер** сверяет результат с задачей и смотрит, как изменения влияют на существующие сценарии. Дополнительно проверяем:

- соблюдены ли слои FSD (steiger ловит не всё — например, логику в `shared`);
- где лежит состояние (см. [Состояние и данные](./state-and-data.md));
- используются ли компоненты `shared/ui` и токены темы, а не свои стили;
- есть ли тесты на новую логику;
- если PR меняет API или общие пакеты — как это влияет на части проекта, которые их используют.

В замечании укажите, что именно вызывает вопрос и почему это важно. Замечания, которые нужно устранить до слияния, обозначайте явно; пожелания — как необязательные.

Автор отвечает на замечания и вносит согласованные исправления в ту же ветку. Обсуждение закрывается после исправления или согласования решения. Если новый коммит сбросил approve, автор запрашивает проверку повторно.

Перед слиянием нужны: минимум один действующий approve от другого участника, закрытые обсуждения и пройденные обязательные проверки CI.

## Проверки на PR

По правилам команды на каждом PR должны проходить: линтинг, проверка FSD, тесты, проверка типов TypeScript и сборка.

Сейчас в CI (`.github/workflows/ci.yml`) работают typecheck, lint (ESLint + steiger), сборка и проверка актуальности клиента Orval. **Тестов и проверки Prettier в CI пока нет** — до их добавления запускайте `pnpm --filter web verify` локально. Для изменений в `apps/api` дополнительно запускайте `pnpm --filter api test` (подробнее — [Инструменты качества и CI](./tooling.md#ci)).

## Секреты и переменные окружения

- В репозитории **нельзя** хранить секреты: пароли, токены, приватные ключи и другие конфиденциальные данные.
- Локально используйте `.env`-файлы с реальными значениями — они исключены из git. Допустим шаблон `.env.example` с названиями переменных и безопасными примерами без реальных секретов.
- Для CI/CD и развёртывания секреты хранятся в защищённых настройках платформы (GitHub Secrets, переменные окружения Netlify и т.п.).
- Секреты не должны попадать в публичную клиентскую сборку: `NEXT_PUBLIC_*` видны в браузере.
- Если секрет случайно попал в коммит или PR — **сообщите команде**. Секрет нужно отозвать или заменить. Удаление последующим коммитом не убирает его из истории git; нужна ли чистка истории — команда решает отдельно.

## Что пока не согласовано

В исходном документе правил эти пункты помечены как предложения или открытые вопросы, поэтому здесь они не описаны: выпуск релизов (релизные ветки, теги, GitHub Release), Draft Pull Request, язык описания PR. Когда команда их утвердит — дополните этот файл.
